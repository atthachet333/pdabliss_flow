## F01 — MariaDB JSON drift

- **Observed.** `migrate diff --from-migrations --to-schema` exited 2 and rendered exactly three `ALTER TABLE … MODIFY … JSON NULL` statements for `appointment_events.fields`, `audit_logs.metadata` and `user_preferences.defaultReminders`. The Prisma schema declares all three as `Json?` and the initial migration creates them as `JSON NULL`. Independent dev and test comparisons against both the schema and replay returned 0.
- **Cause.** This Prisma 7.10.1 migration-replay path normalizes MariaDB’s JSON alias differently from direct datasource introspection. `SHOW CREATE TABLE` on dev, test and the reconstructed shadow showed nullable `LONGTEXT CHARACTER SET utf8mb4 COLLATE utf8mb4_bin` with exact, enabled `JSON_VALID` checks. [MariaDB JSON type](https://mariadb.com/docs/server/reference/data-types/string-data-types/json) · [Prisma replay behavior](https://github.com/prisma/orm/issues/27737)
- **Repair.** The guarded CLI accepts that entire three-statement replay diff only, checks the three database targets and verifies the exact column DDL on each. Other replay differences and any differences in direct comparisons fail. The initial migration and Prisma schema stay byte-identical. Existing serialization, nullability and database-side validation are preserved.
- **Verified.** `node scripts/db.mjs drift` exited 0. Three regressions verify the exact match and reject extra or missing statements, changed types and nullability, wrong charset or collation, and missing or widened `JSON_VALID` checks. A future MariaDB DDL rendering change may require reviewing the narrow matcher. Evidence is in `.qa/ep02.1/baseline-json-metadata.log`, `.qa/ep02/v04-drift.log` and `.qa/ep02/v07-test.log`.

## F04 — Runtime database failure

- **Observed.** The authenticated E14 request returned 500 for `/api/v1/me`, while login returned 503. The v1 plugin installed an encapsulated Fastify error handler. Database errors from rate limiting, session resolution, actor lookup or route work reached that handler before the root handler and were logged as raw errors. The root check also accepted whole Prisma error classes, including ordinary query and conflict errors. The LINE status route’s `try` block covered both LINE reads and the database-backed summary.
- **Repair.** A single handler preserves domain errors and uses an allowlist of connection and pool failure codes from Prisma, MariaDB and the adapter. It returns `503 DATABASE_UNAVAILABLE` with `Retry-After: 30`, a request ID and a generic message. Structured logs include only the allowlisted code. LINE status handles its upstream calls separately so a failure reading the database summary follows the same contract. An unexpected programming error remains a sanitized 500.
- **Verified.** Unit coverage exercises the rate limiter, session lookup and actor lookup across `/api/v1/me`, `/api/v1/today` and `/api/auth/session`. The mutation test injects a database failure at transaction entry and verifies that the same idempotent request creates the appointment once after recovery. Failure responses contain only the error envelope, issue no cookie and omit test private data and raw error details. A MariaDB integration test cuts only its own loopback relay connections, verifies 503 with the sanitized `ECONNRESET` classification and recovers the same session after reopening the relay. Evidence is in `.qa/ep02/v07-test.log`, `.qa/ep02/v08-test-db.log` and `.qa/ep02/v11-smoke.log`.

## F05 — Invitation redemption contention

- **Observed.** Shared scenario S2 returned `[200, 500]` on MariaDB. A synthetic transaction-level reproduction isolated Prisma `P2039` wrapping MariaDB `1020` (`ER_CHECKREAD`, a record changed after the read) at the existing conditional update under `REPEATABLE-READ`. The reproduction emitted only structured codes. [MariaDB error 1020](https://mariadb.com/docs/server/reference/error-codes/mariadb-error-codes-1000-to-1099/e1020)
- **Repair.** PrismaStore translates `P2034` and `P2039` specifically wrapping `1020` into a typed transaction conflict. Invitation redemption and access decisions retry that conflict up to four total attempts with fresh transaction reads. The conditional database write still decides the winner. The retry rechecks state and returns 410 `INVITATION_USED` for a spent invitation or 409 `REQUEST_ALREADY_DECIDED` for a losing approval decision. Permanent failures propagate, and the database transaction covers access request, user state and audit changes.
- **Verified.** The original S2 now returns `[200, 410]`. A 12-round test across two independent Prisma pools checks six two-way and six five-way races, all loser codes, replay, 12 approval-versus-rejection races and final request, account and membership state. The preflight and final runs each passed all 12 rounds. An audit failure test verifies rollback of the invitation, pending request and account state and confirms the failure gets one attempt. The expired, revoked and invalid link checks remain in S2b. Prolonged contention beyond the retry budget remains an internal error. Evidence is in `.qa/ep02.1/baseline-invitation-diagnostic.log`, `.qa/ep02.1/baseline-test-db.log`, `.qa/ep02.1/test-db-first.log` and `.qa/ep02/v08-test-db.log`.
